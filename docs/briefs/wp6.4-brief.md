## Why

Phase 6's second capability is macOS (owner: "make it macos compatible", Apple Silicon, CPU path, spec N1 v0.6.0). WP6.2 audited every platform assumption from the code without a Mac and produced the change list (172 rows; the product's 74). Three design decisions came out of its accept (AD-35 VideoToolbox, AD-36 guard form + dual-target static gate, AD-37 POSIX spawn) and the AD-25(a) Library amendment; four debt rows were opened. This package implements that list ON WINDOWS with Windows-side tests that discriminate (the W rows) and writes the native tests (the M rows) that WP6.5 runs on the owner's Mac, so WP6.5 is a build-and-measure package, not a porting package. The Windows product must not move: the serial gate figures, the NVENC command line and the look are the controls.

## The design (CHARC's pass; the cell builds this unless round 0 disputes it with evidence)

1. **The encoder roster (AD-35; P07, P09, P11, P37, P62).** `capability.py` gets a per-platform roster through the AD-36 statement form: win32 `(hevc_nvenc, libx265)`, darwin `(hevc_videotoolbox, libx265)`, else `(libx265,)`. Availability and bit depth stay the existing TRIAL model: a real one-frame encode per depth through the AD-23 helper, the resolved FFmpeg path and the process cache; VT's trials add `-allow_sw 0` so a software fallback never reads as hardware; 8-bit `yuv420p` / `main`, 10-bit `p010le` / `main10`; a failed 10-bit trial disables 10-bit only. The `EncoderCapability` shape is reused (independent `bit_depths`, `hardware` flag). "auto" = the platform's first available roster entry; an explicit or saved name outside the platform's roster is kept and shown as unavailable with a reason (D26), never silently replaced. Reasons: the NVENC stderr markers stay scoped to NVENC (P10); VT gets its own ASCII-safe diagnostic fragment list (from the captured listing / help text) and the generic tail otherwise.
2. **The VT command branch (P12, P14, P59, P60, P61).** `encode.py` gains an explicit `hevc_videotoolbox` branch beside NVENC and x265: never x265 `-preset` / `-crf` / `-x265-params`, never NVENC `-rc` / `-tier` / `-level` / `-bufsize`. Pixel formats as item 1; `encode_filter` (AD-10) unchanged; the `-vf` chain still ends in `format=yuv420p10le` for 10-bit and FFmpeg converts to `p010le` as it does for NVENC. Rate: a new internal helper (`encode.py`, NOT the frozen `SinkReport`) exposes `nvenc_rate`'s numeric R (H0 = floor(0.24 w h fps), the Main-tier source cap, the 1 / 2 / 4 divisors, the lowest fitting Main-tier level's cap) WITHOUT changing `nvenc_rate`'s behaviour or its NVENC callers (the snapshot test proves it). The VT branch applies BOTH Q1 candidates behind a module-level selector `VT_RATE_CONTROL = "A" | "B"` (default `"B"`: `-b:v R -maxrate R`; `"A"`: `-q:v <Q_LEVEL per quality>` plus `-maxrate R`, with PLACEHOLDER Q_LEVEL values 65 / 55 / 45 marked "WP6.5 measures"), and the geometry refusal of `_prepare` applies to VT as to NVENC (P60). `VideoSink.nvenc_rate` keeps its NVENC meaning; VT's rate state is a separate private attribute (P61). The report records the exact VT argument list per depth and quality for WP6.5.
3. **The spawn helper and the pipe (AD-37, AD-36; P02, P03, P65, P74).** `pipes.py`: the guard becomes the statement form; on win32 `creationflags=CREATE_NO_WINDOW`, else `start_new_session=True`; the darwin default-pipe fallback logs INFO off Windows (WARNING stays on Windows where it would be a defect); nothing else. ## Questions (CHARC's recommended answers; a round-0 dispute with evidence is a STOP to CHARC)

- **Q1 the VT rate selector default.** Recommended `"B"` (`-b:v` + `-maxrate` = R): it is the control whose ceiling FFmpeg maps to a DataRateLimits request (report section 4, DOC [FF]) so the D87 / DR-48 disk estimate has a chance of being conservative; candidate A's q:v placeholder values are for WP6.5's measurement and must be labelled so in code and report. WP6.5 may flip the default on its evidence (an AD-35 amendment then).
- **Q2 the VT listing fixture.** Recommended: a captured text from a real arm64 FFmpeg build if the cell can obtain one offline from the repository's own evidence or the FFmpeg source's documented output; else a SYNTHETIC minimal listing clearly marked, replaced by WP6.5's capture. The product's parsing must not depend on more than the encoder name line and the help text's `-allow_sw` option presence.
- **Q3 the darwin AD-9 reason text.** Recommended as item 7 (`"CPU: graphics-card processing is not available on macOS"`). Alternative: keep "CPU: CuPy not installed" everywhere (true but misleading on a Mac where nothing can be installed).
- **Q4 `tools/footage_guard.py` vs. reusing `jobs/`'s product check.** Recommended: a small tools-side helper (tools must not import product internals that may change; the product's check stays in `jobs/`), with ONE test asserting both give the same verdict on the shared corpus.
