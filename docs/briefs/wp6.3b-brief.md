## Why

1.0.0 ships as a source install with uv; the owner wants a deployable distributable (Phase 6 D-A / D-D / D-F). WP6.1 built and proved the one-folder form and CP6a chose it. What is missing is the repeatable path from a tag to a downloadable zip: the build on a clean runner (so nothing from this laptop leaks in), the bundled FFmpeg with its licence obligations met (the laptop's 9.0.2 gyan.dev build was used only for the PATH-less proof and its licence was NOT recorded, WP6.1 section 4), the artifact's own notices (the 1.0.0 file explicitly covers a source install and says "any future binary redistributor must independently meet source-delivery and other licence obligations"), a headless check that the built artifact behaves (the WP6.1 refusal rows and the worker's bad-request exit need no window), and the two documents a user and the orchestrator follow.

## The design (CHARC's pass; the cell builds this unless round 0 disputes it with evidence)

1. **The workflow** (`.github/workflows/release.yml`): triggers `workflow_dispatch` (input `version`, must equal the tag's) and `push` of tags `v*`. One job `windows` on `windows-latest`: checkout the ref; `astral-sh/setup-uv` (pinned SHA); `uv sync --frozen --no-default-groups --group dev --extra gpu` (the gpu extra is needed because `build.py`'s hidden-import scan reads the eleven locked distributions' RECORDs from the venv; the time is recorded; Q2 offers the alternative); the version check (`clearwater.__version__` equals the tag without `v`, else fail); the tests: `uv run pytest -q -n 4 --timeout 600 -m "not gpu and not footage and not gui and not slow and not fullclip" --basetemp=work/ci-parallel` (the parallel leg only; the serial leg needs footage and the GPU; the local release gate covers them before the tag); the build: `uv run python tools/package/build.py --form onedir --ffmpeg-from <url> --ffmpeg-sha256 <hex> --notices --smoke --zip --out work/release`; upload the zip, its `.sha256` and the notices as workflow artifacts; a second job `release` (needs `windows`, only on a tag): `softprops/action-gh-release` (pinned SHA) creating a DRAFT release for the tag with the three files attached and the release notes body from `docs/release-notes-1.1.0.md` if present. Secrets: none beyond `GITHUB_TOKEN`. Concurrency: one run per ref.
2. **The FFmpeg bundle rule** (`tools/package/ffmpeg.lock.json`): the cell pins ONE Windows x64 FFmpeg release build whose provider publishes (a) the exact FFmpeg release tag, (b) the configure line, (c) the list of linked libraries with versions, and (d) a way to obtain the corresponding source of every GPL / LGPL component (the provider's source bundle, or the build scripts naming each component's release so each source URL can be listed). Q1 names the recommended provider. The lock records provider, FFmpeg version, archive URL, archive sha256, the configure line verbatim, and per component: name, version, licence, source URL. `build.py --ffmpeg-from` downloads the archive to `<out>/ffmpeg/`, verifies the sha256, extracts `ffmpeg.exe`, `ffprobe.exe` and the build's licence/readme files beside `Clearwater.exe` (a `ffmpeg-LICENSE.txt` and `ffmpeg-BUILD.txt` with the configure line), runs each `-version` from the release folder with only that folder on PATH (as `--with-ffmpeg` did) and checks the printed version equals the lock's and the configure line matches the lock's. `--with-ffmpeg` (the PATH copy) stays for local spikes, marked "not for release".
3. **The artifact notices** (`tools/package/notices.py --notices`, written to `<release folder>/THIRD_PARTY_NOTICES.md`): generated from (a) the 1.0.0 audit rows for every distribution that the bundle actually carries (read from the built folder's `_internal` and the PYZ, matched to `uv.lock` names; the runtime rows minus the GPU rows that are NOT bundled, plus their "user-obtained" statement for the pack), (b) the PyInstaller bootloader and run-time hooks rows with the licence and the Bootloader Exception text verbatim from PyInstaller's `COPYING.txt`, (c) the FFmpeg rows from `ffmpeg.lock.json` with every component's licence and source URL, GPL-3.0 text once, (d) the Qt / Shiboken LGPL-3 statement for a REDISTRIBUTED dynamically linked Qt (the user may replace the Qt DLLs; the source URL of the exact Qt release; the LGPL-3 text), (e) pillow-heif's bundled `libx265` (GPL-2.0-or-later), `libheif`, `libde265`, `libstdc++` with their source releases (pillow-heif's wheel names them; the cell reads the wheel's licence folder), (f) numpy / scipy / Pillow / OpenSSL / Python rows as in 1.0.0 with "redistributed in this artifact" verdicts, (g) a header stating that Clearwater is GPL-2.0-or-later, that the artifact is a combined work distributed under GPL-3.0 terms where a GPL-3.0 component (FFmpeg) requires it (the or-later grant allows it; the 1.0.0 file already says so), and where to get the corresponding source of every component. The full licence texts are copied from the installed wheels' licence files and the FFmpeg archive, as the 1.0.0 file did. A test regenerates the notices from a synthetic folder and checks every bundled top-level entry has a row (no entry without a row; no row without an entry, except the pack's user-obtained rows).
4. **The headless smoke** (`build.py --smoke <release folder>`, also run by the workflow): with a redirected `LOCALAPPDATA` / `APPDATA` under `<out>/smoke/` and PATH = System32 only: the ten WP6.1 refusal rows (each exit 2, one stderr line, no window: on the runner no desktop exists, so the window check is "no process left after 60 s"); `Clearwater.exe --export-worker` with an empty stdin -> exit 2 "no request document on stdin"; `Clearwater.exe --export-worker` with a bad request -> exit 2; `ffmpeg.exe -version` and `ffprobe.exe -version` from the folder; the bundle check and the hidden-import check re-read from the built folder; the notices file present with the expected row count; total size and the largest entries printed. No GUI is launched (CLAUDE.md's rules apply on the laptop; on the runner there is no desktop). A failure is a non-zero exit that fails the workflow.
5. **The zip** (`--zip`): `Clearwater-<version>-windows-onedir.zip` with the release folder as its single top-level folder (so unzipping gives one folder), deterministic member order and timestamps (the tag's commit time), and `<zip>.sha256` beside it. The smoke runs on the FOLDER before zipping and the zip is listed after (member count equals the folder's file count).
6. **Cache variables (WP6.1 report, "For WP6.3"):** frozen only, before the pack is activated and before any CuPy import: `CUDA_CACHE_PATH = <cache root>/nvidia-compute-cache` and `CUPY_CACHE_DIR = <cache root>/cupy-kernel-cache` (`config/paths.py`'s cache dir, `app_locations().cache_dir`), set with `os.environ.setdefault` (a user's explicit setting wins). Otherwise the driver writes to the real `%APPDATA%\NVIDIA\ComputeCache` and CuPy to `%USERPROFILE%\.cupy\kernel_cache`, outside Clearwater's folders. One test per variable (the value under a redirected root; not set when not frozen; not overridden when present). The cell names the file at round 0 (`app/startup.py`'s start-up path or `__main__.py` before `gpu_pack.activate()`; CHARC prefers `__main__.py` beside the activate calls, both branches, so the worker gets it too).
7. **The release checklist v2** (`docs/release-checklist.md`): the 1.0.0 steps kept where they still apply, then: the version bump commit (pyproject, `__init__`, notices title) on the owner's "tag 1.1.0"; the local release gate on that commit (the three legs + harness, as 1.0.0); the tag; the owner's push (the harness never pushes); the workflow run watched by the orchestrator (the run URL, the job log archived); the artifact downloaded from the draft release and checked on a CLEAN Windows user account on this laptop (a new local account with no Python, no FFmpeg, no PATH entries: unzip, start, open a photo, export, Tools > Install GPU support, restart, export on the GPU; the owner or the orchestrator by hand; the Entry-point and Desktop-input rules bind the harness, the owner's hand is free); the sha256 of the downloaded zip against the sidecar; the release record; the draft release published by the owner's click. STOP conditions named at each step.
8. **The user guide** (`docs/user-guide.md`): section 2 becomes "Install on Windows 11": download the zip from the release page, check its sha256 (optional), unzip anywhere the user can write (not Program Files unless they choose; the app writes only under `%APPDATA%\Clearwater` and `%LOCALAPPDATA%\Clearwater`), run `Clearwater.exe`; the SmartScreen "unknown publisher" step ("More info" > "Run anyway") with one sentence on why (unsigned, N14); the GPU paragraph from 6.3a (Tools > Install GPU support..., the restart, the EULA statement, the size); the driver requirement kept; the developer install (uv) moved to a short subsection at the end of section 2. Section 6's FFmpeg-not-found text becomes "the bundled FFmpeg is beside Clearwater.exe; if you moved it, put it back". Section 7 drops "no packaged executable". Section 8 names the artifact's notices file.

## Questions (CHARC's recommended answers; a round-0 dispute with evidence is a STOP to CHARC)

- **Q1 the FFmpeg provider.** Recommended: **BtbN's FFmpeg-Builds** (`github.com/BtbN/FFmpeg-Builds`), the `win64-gpl` (NOT `gpl-shared`, NOT any `nonfree`) build of a tagged FFmpeg RELEASE (`ffmpeg-n<version>-...-win64-gpl-<version>.zip`), because the build scripts are public, each linked library's version is pinned in the repository at the build's commit, the builds carry a `LICENSE.txt`, and the release assets are stable URLs with checksums; the corresponding source of every component is the component's release named by the build scripts, which the lock lists. The laptop's gyan.dev 9.0.2 build is NOT recommended for the artifact unless the cell finds gyan.dev publishes the corresponding source bundle for that exact build (it publishes a component list; the cell checks and records; if it does, gyan.dev is acceptable and the product has been validated on it). Whichever is chosen: the same FFmpeg MAJOR version as the laptop's (9.x) so D26's encoder behaviour and the V4 instrument's equivalences hold; a different major is a STOP (the gate would need the serial leg on the bundled binary). The cell's licence read of the chosen build (every `--enable-lib*` in the configure line mapped to a licence) is in the report; any component that is not GPL-compatible is a STOP to CHARC, and that goes to the owner.
- **Q2 the gpu extra on the runner.** Recommended: install it (`--extra gpu`; about 2.4 GB from PyPI, a few minutes on GitHub's network; the runner has 14 GB free) because the hidden-import scan and PyInstaller's analysis both want the real distributions on disk, exactly as the laptop build does; a build that scans differently from the laptop's is a second configuration to prove. Alternative: `build.py` downloads the eleven wheels to a temp folder and scans them unpacked (6.3a's downloader could do it); fewer bytes, one more path.
- **Q3 the runner's missing CUDA at PyInstaller analysis.** PyInstaller imports CuPy at analysis time (WP6.1's build logs show the "CUDA path could not be detected" warning from that process). On the runner there is no NVIDIA driver; CuPy imports without a driver (the warning only), so the analysis proceeds. If it does not, the cell adds `--exclude-module cupy` to the analysis (it is already excluded from the BUNDLE) and records it; a STOP only if PyInstaller cannot analyse the entry script without importing CuPy.
- **Q4 the version check.** Recommended: the workflow fails if the tag's version differs from `clearwater.__version__` (no auto-bump in CI; the bump is a reviewed commit on the owner's word).

## CHARC additions (gen 16, 2026-11-04 ~19:20Z, from WP-DR125 Reviewer B r1b; binding on the fill)

- **`--disable-windowed-traceback` in `build.py`'s PyInstaller arguments (6.3b owns `build.py`).** Today any unhandled exception in ANY frozen process (the GUI, the worker, a `-m` re-entry, the headless rows) opens PyInstaller's modal traceback dialog: a child hangs its parent, and a dialog appears with nobody watching it. With the flag an unhandled exception exits non-zero, which AD-31's parent already handles.
- **Companion, REQUIRED (the product has NO exception hook today; without one the flag turns a GUI start-up failure into a silent exit):** a product exception hook installed at every entry (`sys.excepthook` and `threading.excepthook`) in the entry module: it writes the traceback to the product log (AD-25's log file) and one line to stderr, then exits non-zero; in the GUI process once Qt is up, it also shows ONE plain message box naming the log file before exiting (no traceback text in the box). Worker and `-m` children: log + stderr + exit only, no window. Owned files gain the entry module(s) for this hook (`src/clearwater/__main__.py` and `app/main.py` as the fill finds them) and its tests (source, Qt offscreen for the box; the frozen smoke of item 4 gains a planted-exception row: exit non-zero, one stderr line, NO window under the UIA watch).
- Record at the accept: AD-38 gains the flag and the hook; the hook is the N1-clean replacement of the bootloader dialog.
