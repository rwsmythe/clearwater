## Why

WP7.1 (Insta360 Studio exports validation) ran the D94 fidelity check, V4, on two corrected exports of the 62 s Insta360 clip (`v4-bench-hevc62q`, `v4-hevc62c`, 2026-11-09, frozen-t7 drivers). Each compare record has 46 items; four MANDATORY items differ and all state one fact: the output video stream lasts 1853855/30000 s where the source lasts 1853854/30000 s (926927/15000); mvhd and both edit-list rows follow. The 1852 frames, the full pts sequence (1849 steps of 1001 and 2 of 1002, sha256-equal), the start offsets, all 2,897 audio packets and the display matrices are SAME. V4 had passed on every GoPro fixture to date.

CHARC's reading of the code (to be confirmed, not assumed): `probe.py:414` stores each edit as `Fraction(segment_duration, movie_timescale)`; Insta360 Studio writes the movie timescale 500000 and the segment duration 30897567, so the edit list's end is 30897567/500000 s. `verify.py:652 presentation_end` returns that end divided by the track time base: 92692701/50 = 1853854.02 ticks. `verify.py:676 frame_end`, when no later sample pts exists (the last frame), takes `presentation_end` and rounds a fractional tick UP (`:699-700`), returning 1853855. The sink sends that as the end sentinel (`encode.py:1312-1313`), and FFmpeg's bitstream filter gives the last frame the duration 1002 where the source has 1001. The track's own duration (`duration_ts`, or the last `stts` entry) is exactly 1853854 ticks and is available on every source Clearwater accepts.
