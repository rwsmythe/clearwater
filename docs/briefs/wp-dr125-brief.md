## Why

WP6.1 found (F-E) that the worker's cancel watcher, a daemon thread blocked in `stdin.readline()` on the request pipe, makes EVERY child that inherits that stdin hang at C-runtime start-up on Windows: a pending synchronous `ReadFile` on the inherited handle blocks the child's own start-up. It was reproduced with a product-free stand-in parent against three children (the frozen CuPy canary, plain CPython `-I -c`, frozen `-c pass`); each hung; without the thread the canary returned in 0.24 s. In 1.0.0 the exposure is latent because every product FFmpeg child sets `stdin=` explicitly (AD-23: `export_process.py` and `encode.py` PIPE, `capability.py`, `decode.py`, `verify.py` DEVNULL); the first third-party spawn without `stdin=` (CuPy's `cuda.pathfinder` canary in the frozen build) hit it. WP6.1 shipped a TEMPORARY frozen-only shim in `__main__` (`isolate_worker_stdin`) so the GPU proof could run; the owner's D6 hand check ran on it.

The same stand-in showed DR-125's crash: it exited 0xC0000005 whenever its daemon thread was still blocked reading stdin at interpreter exit, and 0 without the thread. The shim moved the crash from fd 0 to the private descriptor without changing it (1 of 12 frozen runs in WP6.1 2b-4 / 2b-6, `_enter_buffered_busy` on `BufferedReader name=3`). The cause is the buffered reader's lock: at interpreter finalisation CPython tries to flush / close the `BufferedReader` whose lock the daemon thread holds inside `readline()`, and the Windows build dies in `_enter_buffered_busy`. The result line and the output are already written and the parent reports the export done (AD-31), so the user sees nothing, but a worker that dies at exit is a wrong exit status in every log and a trap for the next change.

## The design (CHARC's pass; the cell builds this unless round 0 disputes it with evidence)

1. **Where.** A new function in `app/export_worker.py`, called by `main()` as its FIRST act after the argument check, before `sys.stdout` is taken over and before ANY import that can spawn a child (the composition root, the backend probe, CuPy). `run()` keeps its `stdin: BinaryIO` parameter for tests, but `main()` passes it the private reader, never `sys.stdin.buffer`.
2. **The isolation (both source and frozen).** `private = os.dup(0)` (PEP 446: not inheritable). Open `os.devnull` read-only and `os.dup2(null, 0)`; close the extra null descriptor. Under the AD-36 statement-form guard, on `win32` ONLY: `ctypes.windll.kernel32.SetStdHandle(STD_INPUT_HANDLE, msvcrt.get_osfhandle(0))` so `subprocess` hands a `stdin=None` child the null device too (the windowed frozen build is a GUI-subsystem process whose CRT does not update the Win32 handle on `dup2`); the `else` branch does nothing more (POSIX children inherit fd 0, now NUL). This is the ONE N1 site; it moves from `__main__` to here. `sys.stdin` is left as is (nothing in the worker reads it after this point; the watcher reads the private descriptor).
3. **Fail-closed, as the shim.** Any `OSError` after the dup (null open, `dup2`, `SetStdHandle` returning 0) closes every descriptor this function opened and ends the worker with ONE stderr line `export worker: stdin isolation failed: <type>` and `EXIT_BAD_REQUEST`-class status 2, before the protocol takeover, any log, any import. The only pass-through is `os.dup(0)` raising `EBADF` (no standard input at all): then there is nothing a child could inherit and the worker continues with an empty reader (the cancel-at-end-of-stdin semantics give an immediate cancel, exactly as a closed pipe would: document it, test it).
4. **The watcher reads the RAW descriptor, not a `BufferedReader`.** `_watch_stdin` takes the private fd and assembles lines itself with `os.read(fd, 65536)` in a loop (split on `\n`, keep a remainder; a line is decoded as today; the cancel line sets the flag and the loop ends; `os.read` returning `b""` or raising `OSError` sets the flag). No `io` object wraps the private fd, so there is no buffer lock for finalisation to contend for: the daemon thread may still be blocked in `os.read` at exit, which CPython abandons safely on Windows and POSIX. The request line is read the same way (the first line through the same assembler), so one reader owns the descriptor.
5. **The exit path.** `main()` returns the status as today. ADD: after the result line is sent and the protocol stream is closed, the worker closes nothing the watcher holds and does NOT try to join the watcher (it is blocked in a syscall until the parent closes the pipe); the daemon flag plus the raw read is the whole mechanism. If round 0 finds any remaining shutdown fault on Windows with the raw reader, the fallback (Q1 (b)) is an explicit `os._exit(status)` after `protocol.close()` and `sys.stderr.flush()`, with the reason recorded; not the default.
6. **`__main__`.** Delete `isolate_worker_stdin`, `STDIN_REFUSAL`, the try/except around the call and the now-unused imports; the frozen branch is `gpu_pack.activate()` then `export_worker.main(arguments[2:])`. The module docstring and `tools/package/README.md` describe the worker-side isolation in one paragraph each. The entry-script read-out that WP6.3's build performs will see the function gone; that is expected.
7. **Threads.** Nothing else changes: the engine's threads, the `_Channel` lock and the logging handler are untouched.

## Questions (CHARC's recommended answers; a round-0 dispute with evidence is a STOP to CHARC)

- **Q1 the exit mechanism.** Recommended (a): the raw-descriptor watcher alone (design item 4), because it removes the lock that finalisation contends for and keeps normal interpreter shutdown (atexit, logging shutdown, the protocol stream's close). Alternative (b): `os._exit(status)` after an explicit flush and close of everything the worker owns; robust but skips every finaliser, so it is the fallback only if (a) leaves a Windows shutdown fault that the 20-run series shows.
- **Q2 the Win32 call.** Recommended: `ctypes` + `msvcrt.get_osfhandle` under the AD-36 guard inside the worker module, as the shim did; NOT a new helper in `io/video/pipes.py` (AD-23's helper is the FFmpeg spawn site, not a process-setup site). The N1 site count stays one; AD-34 is amended at the accept.
- **Q3 `sys.stdin`.** Recommended: leave `sys.stdin` bound to the original object; after `dup2` it reads NUL (EOF), which is the safe behaviour for any stray read. Do not rebind it to the private descriptor (the whole point is that only the watcher reads the pipe).
