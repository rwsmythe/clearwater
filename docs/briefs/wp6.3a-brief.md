## Why

CP6a chose the one-folder artifact without CuPy or CUDA (owner D-C amendment: "auto-download of the cuda libraries rather than bundle"; spec N14). WP6.1 proved the loader on a pack filled BY HAND (`uv pip install --target`, a stray `.lock` removed, `write_manifest`), which no user can do. This package is the user's path. The loader already defines what a valid pack is (AD-33: the manifest against the lock, RECORD hashes, ownership, wheel tags; the full check hashes every file). The downloader's whole job is to PRODUCE a pack the full check accepts, and to leave nothing when it cannot.

## The design (CHARC's pass; the cell builds this unless round 0 disputes it with evidence)

1. **The table.** `gpu_pack.LockedDistribution.wheels` rows become `(file name, sha256, url, size)` from `uv.lock` (the lock carries all four); the existing test that keeps the table equal to the lock checks all four. The platform's wheel per distribution is the one whose tags fit (`tag_fits`, as the loader); on `win32` + cp312 that is eleven wheels. The plan = those eleven (name, version, file name, sha256, url, size), the total size, and the stamp `STAMP`.
2. **Preconditions** (all before any network): `pack_root()` is not None (else "GPU support is not available on this platform"); the destination `<root>/<stamp>` does not already hold a pack the CHEAP check accepts (else "GPU support is already installed"; a rejected pack is REPLACED after the user confirms, its folder removed first); free space on the root's volume at least the installed size plus the download size plus 10 % (`shutil.disk_usage`; the message names the figures); the root is creatable (`mkdir(parents=True, exist_ok=True)`).
3. **Staging.** Everything happens under `<root>/<stamp>.partial-<uuid4 hex>/` (`site-packages/` and `downloads/` inside). On success the folder is renamed to `<root>/<stamp>` as the LAST step (atomic on one volume; `os.replace`); the manifest is written INSIDE the staging folder just before the rename. On any failure or cancel the staging folder is removed whole (`shutil.rmtree`, errors logged, never raised past the result). At start of an install, any `<stamp>.partial-*` folder left by a dead process is removed first (the D85 habit).
4. **Download.** Per wheel, in the plan's order: HTTPS GET of the table's URL with `urllib.request` and `ssl.create_default_context()`, a `User-Agent` of `Clearwater/<version>`, a 30 s socket timeout, streamed in 1 MiB chunks into `downloads/<file name>.part` while a `hashlib.sha256` runs; progress reported per chunk (bytes done / total bytes, the wheel's name); the cancel flag checked per chunk. At the end: the byte count equals the table's size and the digest equals the table's sha256, else the wheel is deleted and the install FAILS with "the download of <file> did not match its recorded hash" (no retry on a hash mismatch: a mismatch is not transient). A transport error (`URLError`, `TimeoutError`, `http.client` errors, a non-200) is retried twice with a 2 s pause, then fails with the error's text. A redirect off `files.pythonhosted.org` is refused (a custom `HTTPRedirectHandler`). The `.part` is renamed to the file name once verified.
5. **Unpack.** Each verified wheel is unpacked with `zipfile` into `site-packages/` with these rules: every member name is validated (no absolute path, no `..`, no drive, no backslash, no member outside `site-packages`; a `.data/` directory in a wheel is a FAIL, none of the eleven has one, assert it); directory entries skipped; symlinks and other non-regular members a FAIL; the wheel's own `RECORD` is written as the installed RECORD unchanged (the loader's ownership and hash checks read it; the downloader adds NO `INSTALLER`, `REQUESTED` or `direct_url.json`, so the installed RECORD equals the wheel's and its sha256 is stable); file modes not preserved (plain files). After each unpack the wheel file in `downloads/` is deleted (the disk budget is the installed size plus one wheel in flight, not both totals; the free-space check in item 2 uses the largest wheel, not the sum, once this is built: state the budget in the report).
6. **Verify, then manifest.** After the eleven: `gpu_pack.pack_problems(<staging>, full=True)`-equivalent on the staging folder (the FULL check: RECORD sha256 per file, sizes, ownership, tags, the unlisted-file walk, the reparse-point rule) MUST return no problem, else FAIL with the first problem's text and the staging removed. Then `manifest.json` (the product's writer, moved from `tools/package/build.py`'s `manifest_document` into `gpu_pack_install.py`, with `build.py` delegating), then the rename. The function returns a `JobResult`-shaped outcome (ok / failure text / the installed path) so the GUI and the headless entry share it.
7. **Removal.** `remove()` deletes `<root>/<stamp>` (and any `.partial-*`) with `shutil.rmtree`; refuses if the folder is not under `pack_root()` (never a user-chosen path). The loader's rule that the pack is loaded only at start-up means a running Clearwater keeps its already-imported CuPy; the dialog says "takes effect at the next start".
8. **The GUI** (`gui/gpu_pack_dialog.py`, wired in `shell.py`): Tools > "Install GPU support..." and Tools > "Remove GPU support" (both hidden when `pack_root()` is None; "Install" disabled while an install runs; "Remove" enabled only when a pack folder exists). The install dialog (window-modal `open()`, never `exec`, as the settings dialog): a text block with the plan (the eleven names and versions, the download and installed sizes, the destination folder), the licence statement (below), an "Install" button, a progress bar + the current wheel's name, "Cancel", and on completion the line "GPU support is installed. Restart Clearwater to use it." The job runs through the existing `QtJobRunner` (G9) with a `Progress` whose `cancelled()` is the dialog's cancel; the dialog never touches the downloader's thread. The idle device reason (`set_idle_device`) is the trigger for a one-line hint in the status bar's tooltip when the reason starts with `CPU: CuPy not installed` and a pack root exists: "Tools > Install GPU support..." (no dialog pops by itself: N14 is on request).
9. **The licence statement** (the dialog's text and the report; CHARC's wording, the owner may read it at the accept): "GPU support downloads CuPy and NVIDIA's CUDA runtime libraries from PyPI into your user folder. The NVIDIA libraries are provided by NVIDIA under the NVIDIA Software License Agreement (the file `License.txt` inside each nvidia package after the install); CuPy is MIT. Clearwater does not redistribute them." The install button's label is "Download and install" and pressing it is the user's request.
10. **The headless entry.** `python -m clearwater --install-gpu-pack` (source) and `Clearwater.exe --install-gpu-pack` (frozen; a windowed executable prints only when its output is redirected, say so in the guide): runs the same function with a line-per-wheel progress on stderr and exit 0 / 1 with the message; `--remove-gpu-pack` likewise. In `__main__.main` the row sits after the PATH step and BEFORE `--export-worker`, applies frozen and source alike (the downloader is useful in source for tests and for a developer), imports no Qt, and takes no further arguments. AD-34's order is amended at the accept.
11. **The `activate()` warning filter** (WP6.1 report, "For WP6.3"): `warnings.filterwarnings("ignore", message="CUDA path could not be detected.*", category=UserWarning)` immediately before the pack goes on the path, frozen only; one test asserts the filter is installed only when frozen and matches that message only.
12. **`CUDA_CACHE_PATH` and `CUPY_CACHE_DIR`:** NOT here; 6.3b sets them in `activate()`'s caller with the cache root (they need `config/paths.py`'s cache dir, which the loader does not know). Listed so round 0 does not ask.

## Tests (the cell writes these; Reviewer A checks they discriminate)

`tests/test_gpu_pack_install.py`, with a `fake_index` fixture: a `http.server.ThreadingHTTPServer` on `127.0.0.1:0` serving a folder of SYNTHETIC wheels (a few files each, a correct `RECORD` with sha256 and sizes, a `WHEEL` with the platform's tags, a `METADATA` naming the distribution and version) built by the test, and a monkeypatched `LOCKED_DISTRIBUTIONS` / `STAMP` naming them with the server's URLs; `pack_root` monkeypatched to `tmp_path`.

- **Happy path:** install succeeds; the folder is `<root>/<stamp>`; `gpu_pack.check_pack` accepts it; the FULL check accepts it; no `.partial-*` remains; the manifest's RECORD hashes equal the installed RECORDs; progress reports were monotonic and the last one is total / total.
- **Hash mismatch** on the third wheel: failure text names the file; nothing under `<root>` remains; the server log shows no further requests after the mismatch.
- **Short body** (the server closes early): the transport retry runs (the server counts requests: 3), then failure; nothing remains.
- **Cancel** mid-second-wheel: cancelled result; nothing remains.
- **Redirect off-host** (the server answers 302 to another host): refused, nothing remains, no second connection made (the test's second server records zero hits).
- **Hostile wheel members** (`../x`, an absolute path, a backslash path, a symlink entry, a `.data/` folder): each FAILS before any file is written outside staging; nothing remains.
- **Already installed:** a valid pack present: the result says so, nothing downloaded (zero server hits). **Rejected pack present:** replaced (removed, then installed).
- **Disk space:** `shutil.disk_usage` monkeypatched low: refusal before any request.
- **Removal:** deletes the pack and a planted `.partial-*`; refuses a path outside the root.
- **Dead-process leftovers:** a planted `.partial-*` is removed at the start of an install.
- **The unlisted-file guard:** a synthetic wheel whose RECORD omits one of its files: the full check fails the install, nothing remains (this is the F-C class caught by the product).
- **The table equals the lock** (extended): name, version, file name, sha256, url and size per wheel, from a parse of `uv.lock` (the existing test's method).
- `tests/test_gui_gpu_pack_dialog.py` (`gui`, offscreen): the dialog opens from the menu action; its text carries the sizes and the statement; the progress bar follows a scripted job; cancel ends it; the completion text appears; the menu enabling follows the pack folder's presence; no `exec()` anywhere (grep).
- `tests/test_frozen_entry.py`: `--install-gpu-pack` dispatches to the installer with Qt not imported (the sibling tests' form), frozen and not frozen.
- `tests/test_tools_package_build.py`: `write_manifest` still produces the same document (delegation).

## Questions (CHARC's recommended answers; a round-0 dispute with evidence is a STOP to CHARC)

- **Q1 URLs in the table vs. the PyPI JSON API.** Recommended: the lock's URLs in the table (deterministic, offline-testable, pinned with the hash; a lock bump updates them with the test). Alternative: resolve the file name through `https://pypi.org/pypi/<name>/<version>/json` at install time (one more host, one more parser, no gain while the lock pins the file).
- **Q2 installed RECORD = the wheel's RECORD.** Recommended yes (item 5); the manifest's RECORD hash is computed from what was written, so the loader's checks are self-consistent; the hand-filled pack's RECORDs (uv-written, with `INSTALLER` etc.) differ in hash but that pack has its own manifest. The census equality in the seat run is the proof that the FILE sets are equal.
- **Q3 one job or one per wheel.** Recommended one job (one progress bar, one cancel, one result; the per-wheel names in the progress text).
